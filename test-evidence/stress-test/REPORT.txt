CrowdWatch - server stress test
===============================

Set-up
  Server:  java -Dcrowdwatch.rateLimit=0 -Xmx512m -jar CrowdWatch.jar --server big.venue 8600 <control-key> <scout-key>
           (the rate limit is switched off because every simulated device comes from 127.0.0.1;
            the limit itself is tested by TC-71)
  Venue:   big.venue (make_venue.py): 400 areas, 760 links, 250 units, 8 exits, automation on
  Load:    javac LoadTest.java Probe.java
           java -DscoutKey=<scout-key> LoadTest 8600 <control-key> <server-pid> baseline venue ramp slow flood
           growth test: venue copy with "archive: 1m", then: LoadTest <port> <key> <pid> growth
  Machine: 4 cores, 16 GB; load generator on the same machine, so maximum rates are a little understated.

Phases
  baseline  one client, one request at a time
  venue     90 s: 250 scout devices (poll every 3 s, acknowledge, go on scene, resolve, rare SOS),
            20 dashboards (5 requests every 3 s), 400 sensors (1 update/s each), 2 reports/s,
            an officer checking in and reviewing automatic dispatches
  ramp      16, 64, 256, 1024 clients sending requests back to back, 15 s each
  slow      4 ... 600 connections that send half a request and wait; is a normal request answered?
  flood     5,000 idle connections
  growth    2,000 / 10,000 / 30,000 incidents created and resolved, then request times and memory

Results (before = first server version, after = delivered version)
  Measure                                        Before                              After
  Busy venue                                     506 req/s, no errors, scout p99 43 ms   508 req/s, no errors, scout p99 5 ms
  One client, small reply                        44 ms, 32 req/s                     1.5 ms, 382 req/s
  1,024 clients                                  3,927 req/s, 17 failed, max 1.5 s   5,361 req/s, 0 failed, max 0.29 s
  Half-sent requests                             4 froze the server                  300: others answered in 1 ms; 600: up to 4.3 s delay
  5,000 idle connections                         answered in 109 ms                  answered in 1 ms
  TREND alerts in the run                        115                                 52
  Radio console lines in the run                 486                                 2
  30,000 incidents: GET /api/summary             12 ms                               1-3 ms (archived)
  30,000 incidents: memory after GC              130-160 MB                          87-98 MB
  30,000 incidents: final save / restart         5.3 s / 3.1 s                       2.2 s / 1.5 s
  Reading data without a key                     allowed                             401

Remaining limits
  - One global lock: about 5,400-5,900 requests/s at most on this machine (about 10x the busy-venue load).
  - 600+ half-sent connections at once can still delay replies by up to 5 s: use a reverse proxy
    (for example nginx) with per-address connection limits and TLS in front of the server.
  - Keys are shared per role, not personal.
